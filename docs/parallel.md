## 1. 무엇을 어떻게 보이나 (안건 10 결정)

서버는 전역 뮤텍스 하나로 `execute()`만 감싸요(4.5절). 그래서 보여 줄 것은 "**DB 부분은 한 번에 하나, 그 밖(네트워크·파싱·응답 전송)은 작업 스레드 수만큼 동시에**"예요. 회의 자료의 추천 묶음을 받아들이고, 아래처럼 정했어요.

| 무엇을 | 어떻게 | 기대 |
| --- | --- | --- |
| 부하 클라이언트 | Python 표준 라이브러리. 클라이언트 하나가 **프로세스 하나**예요(16개). 스레드로 만들면 GIL 때문에 보내는 쪽이 먼저 막혀요 | — |
| 처리량 표 | 서버 `--threads` 1·2·4·8 × 작업 4가지, 각 5초, 요청마다 새 연결(4.2절) | 아래 줄들 |
| 　id 조회만 | `SELECT … WHERE id = 무작위` | 잠금 안 시간이 µs라 서버 한 스레드로도 빨라요. 같은 기계의 클라이언트가 먼저 한계일 거예요(추론) |
| 　name 조회만 | `SELECT … WHERE name = 'user<무작위>'` (전체 순회) | 잠금 안 시간이 길어서 스레드 수와 상관없이 같아요 |
| 　id 80% + INSERT 20% | 조회 사이에 INSERT를 섞어요 | id 조회와 비슷해요 |
| 　**느린 업로드** | `Expect: 100-continue`로 헤더를 보내고, 서버의 `100 Continue`를 받은 뒤 100ms 쉬고 본문을 보내요(curl이 느린 회선에서 큰 본문을 올릴 때와 같은 모양) | 작업 스레드 하나가 100ms를 잠금 **밖**에서 기다려요. 처리량이 스레드 수에 비례해요 |
| 막힘 확인 | 서버 스레드 8. id 조회 클라이언트 1개의 응답 시간을 혼자일 때와 name 조회 클라이언트 2개가 계속 도는 동안으로 비교. 두 부하는 같은 시계로 시작 시각을 정하고(name `[t, t+D+2]`, id `[t+1, t+1+D]`), 실제 첫 요청·마지막 응답 시각으로 name 부하가 id 측정을 덮었는지 확인해요 | 4.7절 추론대로 id 조회가 name 조회 하나 길이만큼 기다려요 |
| 정확성 | 빈 테이블에 클라이언트 16개가 INSERT 10,000건을 동시에. 응답 id 중복·빈틈, `SELECT *` 결과와 응답의 id·name·age 일치, 강제 종료(Ctrl+C와 같음) 뒤 재시작해서 같은지, 다음 id | 모두 통과 |
| 데이터 경쟁 | 서버를 `-fsanitize=thread`로 빌드해 위 작업을 모두 돌리고 서버 표준 오류의 `WARNING: ThreadSanitizer` 줄 수를 세요. 먼저 일부러 경쟁을 만든 작은 프로그램으로 TSan이 실제로 잡는지 확인해요 | 서버 0건, 시험 프로그램 1건 |

- **느린 업로드를 `100 Continue` 뒤에 쉬는 이유:** 헤더 바로 뒤에 쉬면 클라이언트 16개가 대기열에 있는 동안 한꺼번에 쉬어요. 그러면 작업 스레드가 그 연결을 꺼낼 때는 본문이 이미 와 있어서 스레드 1개도 8개와 같은 처리량이 나와요(처음 시도에서 모두 157 req/s). `100 Continue`는 그 연결을 꺼낸 작업 스레드가 보내므로, 그 뒤에 쉬어야 스레드 하나가 실제로 묶여요.
- 응답은 모두 내용까지 확인해요. 조회는 행 1개이고 `id`·`name = user<id>`·`age = id % 100`이 맞아야 하고, INSERT는 `ok: true`, `type: insert`, 정수 `id`여야 해요(정확성 검사와 재시작 뒤 INSERT도 같아요). 측정 구간이 끝난 뒤 도착한 응답도 검사해요. 처리량과 응답 시간에만 넣지 않아요.
- 하나라도 틀리거나, HTTP 오류·연결 오류(응답 없이 닫힘, 잘린 응답 포함)가 있거나, 표본이 없는 실행이 있거나, 서버 표준 오류를 읽지 못했거나, TSan 보고가 있으면 스크립트가 종료 코드 1이에요. 인자가 잘못되면(시간이 유한한 양수가 아님, `--inserts` 0 등) 시작 전에 종료 코드 2예요.
- `--data`는 시작할 때 한 번 임시 복사본으로 고정해요. 모든 서버와 클라이언트의 id 범위가 그 복사본을 기준으로 해요.

## 2. 실행 방법

```bash
# 측정용 데이터 (이름 user<id>, 나이 id % 100). bench/index_bench.c는 docs/bench.md 참고
gcc -std=c11 -Wall -Wextra -Wpedantic -Werror -O2 -I. -pthread bench/index_bench.c -o index_bench
./index_bench bench_1m.sans 1000000 10 20 0 > /dev/null

# 서버와 부하 (약 3분)
gcc -std=c11 -Wall -Wextra -Werror -pedantic -O2 -pthread server.c parser.c execute.c storage.c bptree.c -o dbms_server
python3 bench/load_test.py --server ./dbms_server --data bench_1m.sans

# ThreadSanitizer (Linux). 먼저 TSan이 실제로 경쟁을 잡는지 확인해요: 경고 1건이 나와야 해요
cat > race.c <<'EOF'
#include <pthread.h>
static int counter;
static void *bump(void *arg) { (void)arg; for (int i = 0; i < 100000; i++) counter++; return NULL; }
int main(void) { pthread_t a, b; pthread_create(&a, NULL, bump, NULL); pthread_create(&b, NULL, bump, NULL);
  pthread_join(a, NULL); pthread_join(b, NULL); return 0; }
EOF
gcc -O1 -g -fsanitize=thread -pthread race.c -o race
setarch "$(uname -m)" -R ./race 2>&1 | grep -c "WARNING: ThreadSanitizer"   # 1

gcc -std=c11 -Wall -Wextra -Werror -pedantic -O1 -g -fsanitize=thread -pthread server.c parser.c execute.c storage.c bptree.c -o dbms_server_tsan
printf '#!/bin/bash\nexec setarch "$(uname -m)" -R "%s/dbms_server_tsan" "$@"\n' "$PWD" > tsan_wrap.sh && chmod +x tsan_wrap.sh
./index_bench bench_100k.sans 100000 10 20 0 > /dev/null
python3 bench/load_test.py --server ./tsan_wrap.sh --data bench_100k.sans --threads 8 --duration 3 --name-duration 3
```

- 주요 인자: `--suite throughput|blocking|correctness|all`, `--threads 1,2,4,8`, `--clients 16`, `--duration 5`, `--name-duration 5`, `--pause 0.1`, `--inserts 10000`.
- 서버는 실행마다 새 임시 디렉터리에서 켜고, `--data`를 `users.sans`로 복사해요. 원본은 바뀌지 않아요.
- **TSan과 주소 무작위화:** WSL2 커널(6.18)에서는 TSan이 주소 무작위화(ASLR)를 끄지 못하면 `FATAL: ThreadSanitizer: encountered an incompatible memory layout`으로 멈춰요. 그래서 `setarch -R`로 끄고 실행해요. Docker 안에서는 기본 seccomp가 이를 막아서, 측정한 컨테이너는 `docker run --security-opt seccomp=unconfined`로 띄웠어요(그 컨테이너 한 번에만 적용되는 옵션이에요).

## 5. 해석과 발표 메시지

- **느린 업로드: 스레드 수에 정확히 비례해요(9.8 → 19.6 → 39.2 → 78.4).** 작업 스레드 하나가 요청 하나의 100ms 대기를 잠금 밖에서 견디고, 다른 스레드는 그동안 다른 요청을 끝내요. 이론값은 `스레드 수 ÷ 0.1초`(10·20·40·80)예요. 스레드 풀이 있어서 느린 클라이언트 하나가 서버 전체를 막지 않는다는 근거예요.
- **name 조회: 스레드 수와 상관없이 초당 23번이에요.** name 조회 하나가 잠금 안에서 약 43ms(100만 행 순회, [bench.md](bench.md) 4.2절)이고 `1 ÷ 0.043 ≈ 23`이에요. 4.5절 "SELECT끼리 동시에 읽지 않아요"가 그대로 보여요. p50이 줄고 p99가 느는 것은 스레드가 많을수록 잠금을 기다리는 요청이 많아지고, 뮤텍스가 순서를 보장하지 않아 운 나쁜 요청이 오래 기다리기 때문으로 봐요(추론).
- **id 조회: 스레드 수와 상관없이 2만 3천~3만 3천 사이에서 흔들려요.** 스레드 수가 늘어도 차례로 오르지 않아요. 같은 코드로 두 번 잰 값이 스레드 1에서 23,415와 28,861, 섞은 작업은 스레드 2에서 19,002와 29,545처럼 실행마다 크게 달라요. 서버 스레드 1개로도 이미 초당 2만 번이 넘어요(잠금 안은 수 µs, [bench.md](bench.md)). 클라이언트 프로세스 16개와 서버가 같은 8코어를 나눠 쓰므로 클라이언트 쪽이 먼저 한계라고 봐요(**추론**, 4.7절 "스레드 수를 바꿔도 처리량이 같으면 클라이언트를 먼저 의심해요"). 어느 쪽이 먼저 한계인지는 따로 재지 않았어요. 확인하려면 다른 기계에서 부하를 보내거나 서버와 클라이언트의 CPU 사용률을 같이 재야 해요.
- **막힘:** name 조회가 도는 동안 id 조회 p50이 0.15ms → 86ms예요. name 조회 클라이언트 2개가 번갈아 잠금을 잡아서, id 조회가 name 조회 약 2개(43ms × 2) 길이를 기다려요. 4.7절 추론("name 조회가 끝날 때까지 기다려요")을 수치로 확인했어요. 선택하지 않은 B(읽기·쓰기 잠금 + `pread`)였다면 조회끼리 기다리지 않았을 거예요(4.5절, 5.4절).
- **정확성:** 동시에 들어온 INSERT 1만 건이 빈틈·중복 없이 1..10,000을 받았고, 강제 종료 뒤에도 그대로예요. "ID 발급 → 레코드 → 헤더 → 인덱스"가 한 잠금 안에 있다는 4.5절 설계가 지켜졌어요.

발표 한 줄: "**DB는 한 번에 하나(name 조회 23/s 고정), 네트워크 대기는 스레드 수만큼 동시에(느린 업로드 10→80/s), 결과는 1만 건 동시 INSERT에도 정확하고 TSan 경고 0.**"

## 6. 한계

- 서버와 클라이언트가 같은 8코어 기계라 id 조회 처리량은 서버 한계가 아니에요. 서버만의 한계는 재지 않았어요.
- 느린 업로드의 100ms는 인위적인 지연이에요. 실제 회선의 대기 시간 분포와는 달라요.
- Docker Desktop(WSL2) 안에서 잰 값이에요. 같은 기계의 Windows(MinGW-w64)에서도 스크립트를 짧게 돌려 정확성(INSERT 500건)과 느린 업로드 비례(9.7 → 19.3 → 38.7 → 77.3)를 확인했지만, Windows는 연결 비용이 커서 id 조회 처리량이 수백 req/s 수준이라 표에 넣지 않았어요.
- TSan은 실제로 실행된 경로만 검사해요. 오류 응답(400·413·503) 경로는 이 부하에서 돌지 않았어요. 그 경로는 `tests/test_server.py`가 보지만 TSan 빌드로 돌리지는 않았어요.
