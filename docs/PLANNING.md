# 과제 요구사항

> 이 문서를 읽으면 Phase마다 무엇을 만들어야 하는지 요구사항 ID로 확인할 수 있어요. 설계 문서와 PR은 이 ID로 요구사항을 가리켜요.

세 단계에 걸쳐 동작하는 미니 DBMS를 직접 구현해요.

| 단계 | 의존 | 핵심 결과물 |
|---|---|---|
| Phase 1 | — | CLI로 INSERT / SELECT가 동작하는 파일 기반 SQL 처리기 |
| Phase 2 | Phase 1 | Phase 1 처리기 + B+ 트리 인덱스 + 100만 건 성능 비교 |
| Phase 3 | Phase 1 + Phase 2 | Phase 1+2를 내부 엔진으로 쓰는 API 서버 + Thread Pool 병렬 처리 |

## Phase 1. SQL 처리기

입력(SQL) → 파싱 → 실행 → 저장 흐름의 처리기를 만들어요.

| ID | 요구사항 |
|---|---|
| R1-1 | 텍스트 파일로 작성한 SQL 문을 Command Line 명령으로 SQL 처리기에 전달해요. |
| R1-2 | 입력된 SQL 문장을 분석해 구조화해요. 최소 `INSERT`, `SELECT`를 지원해요. |
| R1-3 | `INSERT`는 데이터를 파일에 추가해요. |
| R1-4 | `SELECT`는 파일에서 데이터를 읽어 출력해요. |
| R1-5 | 각 테이블은 파일로 관리해요. |
| R1-6 | 저장 포맷은 자유롭게 설계해요. (CSV, binary, custom 등) |
| R1-7 | schema와 table은 이미 있다고 가정해요. `CREATE TABLE`은 구현하지 않아도 돼요. |

중점: 처리기 구조, 파일 기반 저장 방식 설계, DB 처리 흐름 이해, CLI 구현.

## Phase 2. B+ 트리 인덱스

실제 DBMS가 쓰는 디스크 기반 B+ 트리를 단순화해 메모리 기반으로 구현해요.

| ID | 요구사항 |
|---|---|
| R2-1 | 메모리 기반 B+ 트리를 구현해요. |
| R2-2 | 테이블에 레코드가 추가되면 ID를 자동으로 부여하고, 그 ID를 B+ 트리에 인덱스로 등록해요. |
| R2-3 | ID 기반 검색(`WHERE id = ?`)에서 B+ 트리 인덱스를 사용해요. |
| R2-4 | 레코드를 최소 1,000,000개 이상 INSERT해요. |
| R2-5 | ID 기준 SELECT(인덱스 사용)와 다른 필드 기준 SELECT(선형 탐색)의 속도 차이를 비교해요. |
| R2-6 | Phase 1의 SQL 처리기를 그대로 사용해 연동해요. |

중점: `WHERE id = ?`에서 B+ 트리를 쓰는 방법, 대용량 레코드를 쉽게 만들고 테스트하는 방법, Phase 1 처리기와의 매끄러운 연결.

## Phase 3. 미니 DBMS — API 서버

| ID | 요구사항 |
|---|---|
| R3-1 | 구현한 API로 외부 클라이언트가 DBMS 기능을 사용할 수 있어요. |
| R3-2 | Thread Pool을 구성하고, 요청이 들어올 때마다 스레드를 할당해 SQL 요청을 병렬로 처리해요. |
| R3-3 | Phase 1의 SQL 처리기와 Phase 2의 B+ 트리 인덱스를 그대로 활용해 내부 DB 엔진을 구성해요. |

중점: 멀티 스레드 동시성 이슈, 내부 DB 엔진과 외부 API 서버 사이 연결 설계, API 서버 아키텍처.

## 공통

| ID | 요구사항 |
|---|---|
| R0-1 | 단위 테스트로 함수를 검증해요. |
| R0-2 | Phase마다 기능 테스트를 해요. Phase 1은 SQL 처리, Phase 2는 B+ 트리 적용(인덱스 사용/미사용 속도 비교 포함), Phase 3은 실행 중인 서버에 대한 API 동작을 확인해요. |
| R0-3 | 엣지 케이스를 최대한 고려해요. |
| R0-4 | AI로 만든 코드도 핵심 로직은 이해하고 설명할 수 있어야 해요. |
| R0-5 | 이력서와 포트폴리오에 넣을 수 있을 만큼 완성도 있게 구현해요. 다른 팀과 차별점이 될 추가 구현도 고민해요. |
