## 1. 무엇을 재나

| 항목 | 방법 |
| --- | --- |
| 데이터 | `users`에 `('user<i>', i % 100)`를 i = 1…N 차례로 INSERT. id는 1…N |
| 열기 | `storage_open()` 한 번(헤더 검사 + 파일 전체 읽기 + 트리 재구축). 5번 재요 |
| 전체 순회 1번 | 열린 상태에서 아무것도 안 하는 콜백으로 `storage_scan()`. 열기 비용 중 "읽기 + 레코드 검사" 몫이에요 |
| 트리만 만들기 | 파일 없이 메모리에서 `bptree_insert()`를 키 1…N 오름차순으로. 열기 비용 중 "트리" 몫이에요 |
| 인덱스 메모리 | 트리를 따라가며 노드 수를 세고 `노드 수 × sizeof(BpNode) + sizeof(BpTree)`. `malloc` 부가 비용은 빼요 |
| ① id + 인덱스 | `storage_find_by_id()` (트리 찾기 + 레코드 1개 읽기 + 검사 + 콜백) |
| ② id 선형 | `storage_scan()`으로 모든 행의 id 비교. 실행기의 필터 경로와 같이 끝까지 읽어요 |
| ③ name 선형 | `storage_scan()`으로 모든 행의 name 비교. 명세가 요구하는 비교군이에요 |

- 조회 대상은 splitmix64(시드 20)로 뽑은 무작위 id 1,000개예요. ③은 같은 id의 이름 `user<id>`를 찾아요. 조회마다 `clock_gettime(CLOCK_MONOTONIC)`으로 재서 평균·중앙값·최소·최대를 내요.
- **정확성:** 조회마다 ①이 넘긴 행과 ②·③이 넘긴 행의 id·name·age·row_index가 같은지 봐요. 없는 id 4개(0, -1, N+1, `INT64_MAX`)는 ①·② 모두 0행이어야 해요. 하나라도 어긋나거나 `bptree_check()`가 실패하면 종료 코드가 1이에요.
- 트리 노드를 세려고 측정 프로그램이 `storage.c`와 `bptree.c`를 `#include`해서 한 번역 단위로 빌드해요. 측정하는 코드는 그대로이고, 공개 헤더에 통계 함수를 더하지 않아요([`bptree.h`](../bptree.h) 주석).
- CLI(`main.c`)에는 측정 코드를 넣지 않았어요(3.5절).

## 2. 빌드와 실행

```bash
gcc -std=c11 -Wall -Wextra -Wpedantic -Werror -O2 -I. -pthread bench/index_bench.c -o index_bench
./index_bench bench.sans                 # 100만 행, 조회 1,000개, 시드 20, ② 포함
./index_bench bench.sans 1000000 1000 20 0   # ② 빼기 (조회 1,000개에 약 1분 줄어요)
```

- 인자: `<파일> [행 수=1000000] [조회 수=1000] [시드=20] [②=1|0]`. 행 수는 1 이상, 조회 수는 1~1,000,000, ②는 `0`이나 `1`만 받아요. 숫자가 아니거나 범위 밖이면 측정하지 않고 종료 코드 2예요.
- 파일이 없으면 행 수만큼 INSERT해서 만들고 삽입 시간도 출력해요. 있으면 행 수가 같고 이 프로그램이 만든 형식(id i의 이름 `user<i>`, 나이 `i % 100`)인지 시간 밖에서 확인한 뒤 그대로 써요. 어긋나면 종료 코드 1이에요. 다른 행 수로 재려면 파일을 지워요.
- 열기·닫기 실패, 시간 읽기 실패, 표준 출력 쓰기 실패도 종료 코드 1이에요.
- `-pthread`는 MinGW-w64에서 `clock_gettime`이 winpthreads에 있어서 필요해요. Linux에서는 영향이 없어요(3.5절).
- `python tests/run_tests.py`는 2,000행·조회 50개로 짧게 돌려(`index_bench_smoke`) 빌드와 결과 일치만 확인해요. 100만 행 측정은 손으로 돌려요.

- 조회마다 ① → ② → ③ 순서로 재요. ③이 ② 바로 뒤라 덕을 보는지 보려고 같은 파일·시드로 ②를 켜고 끈 실행을 이어서 비교했어요(Linux). ③ 중앙값이 ② 켬 43.33ms, ② 끔(① → ③) 43.87ms라 순서 효과는 측정 흔들림 안이에요. 파일 전체가 이미 페이지 캐시에 있어서로 봐요(3장, 추론).
- 열기 ≈ 전체 순회 + 트리만 만들기예요(Linux 41.8 + 29.8 = 71.6ms, Windows 63.9 + 28.9 = 92.8ms). 트리 비용은 두 환경이 같고, 차이는 파일 읽기에서 나요.

## 5. CLI 한 번 실행 비용

시연에서는 CLI로 SQL 파일을 돌리므로, 같은 100만 행 파일로 문장 하나짜리 SQL 파일을 실행해 프로세스 시작부터 끝까지 재 봤어요. Linux, `-O2`로 빌드한 `dbms`, 7번씩 잰 값이에요.

CLI는 현재 디렉터리의 `users.sans`만 열어요. 그래서 빈 작업 디렉터리를 만들고 측정 파일을 `users.sans`로 두고 재요.

```bash
gcc -std=c11 -Wall -Wextra -Werror -pedantic -O2 main.c parser.c execute.c storage.c bptree.c -o dbms
mkdir cli_bench && cd cli_bench
../index_bench users.sans 1000000 10 20 0 > /dev/null   # 측정용 100만 행을 users.sans로 만들기
echo "SELECT * FROM users WHERE id = 777777;" > id.sql
echo "SELECT * FROM users WHERE name = 'user777777';" > name.sql
: > empty.sql
../dbms id.sql && ../dbms name.sql    # 둘 다 "777777	user777777	77"과 "SELECT OK rows=1"인지 먼저 확인
for f in empty id name; do for i in 1 2 3 4 5 6 7; do
  s=$(date +%s%N); ../dbms $f.sql > /dev/null; e=$(date +%s%N); echo "$f $(( (e - s) / 1000000 ))ms"
done; done
```

| SQL 파일 | 7번 (ms) | 중앙값 |
| --- | --- | --- |
| 빈 파일 | 82 74 77 73 80 74 74 | 74ms |
| `SELECT * FROM users WHERE id = 777777;` | 73 72 82 75 74 75 75 | 75ms |
| `SELECT * FROM users WHERE name = 'user777777';` | 118 116 116 120 118 113 117 | 117ms |

- 실행마다 열 때 트리를 다시 만들어서(4.2절 열기 약 69ms), 빈 파일도 74ms가 걸려요. id 조회 하나는 그 위에 몇 µs만 더해요.
- name 조회는 열기 비용 위에 전체 순회(약 43ms)를 한 번 더 해요.

## 6. 해석

- **인덱스 조회는 행 수와 거의 무관해요.** 높이 3인 트리를 내려가 레코드 하나만 읽어요. 선형 조회는 100만 행 전체(80MB)를 읽고 검사해요.
- **구축은 실행마다 한 번 내는 비용이에요.** 열기 약 69ms(Linux) 중 트리 몫은 약 30ms이고, 나머지는 파일 읽기예요. id 조회 하나가 선형보다 약 43ms 아끼므로, 한 번 켜서 id 조회를 2개 이상 하면 구축 비용을 넘어서요(69 ÷ 43 ≈ 1.6). Phase 3 서버는 한 번 켜 두고 계속 조회하므로 이 비용은 시작할 때 한 번이에요.
- **Phase 1과 달라진 점:** Phase 1의 열기는 헤더만 읽었어요. 지금은 빈 SQL 파일도 열 때 파일 전체를 읽어요(5장). 계획 3.3절에서 받아들인 대가예요.
- **[계획 5장 참고 측정값](phase2-3.md#5-참고-측정값)과 비교:** 시제품을 다른 PC(Ryzen 7 5800X, tmpfs)에서 잰 값은 ① 3.3µs, ③ 71.9ms, 인덱스 만들기 약 140ms(중앙값)였어요. ①은 비슷하고, ③과 구축은 이번이 더 빨라요. 기계와 파일 시스템이 달라 원인은 따로 확인하지 않았어요.
- Windows의 ①이 Linux의 약 2배인 것은 조회마다 하는 64비트 위치 이동과 `fread`가 더 비싸서로 보여요(추론, 따로 재지 않음).
- **삽입 속도:** 100만 행 INSERT는 Linux 1.37초, Windows 4.25초예요. INSERT마다 레코드와 헤더를 각각 flush하는 지금 설계로도 시연에 문제없는 수준이라, [저장 설계 10장](storage.md#10-정하지-않은-것)의 "닫을 때만 헤더 쓰기"는 다시 정하지 않아요.

## 7. 한계

- 한 PC에서 한 번 잰 값이에요. 다른 프로그램의 영향은 따로 막지 않았어요.
- 파일을 만든 직후라 페이지 캐시에서 읽어요. 디스크에서 처음 읽는 경우(캐시를 비운 뒤)는 재지 않았어요.
- Linux 측정은 Docker Desktop(WSL2) 안이라 순수 Linux 기계와 파일 입출력 비용이 다를 수 있어요.
- 인덱스 메모리는 노드 크기만 셌어요. `malloc`이 노드마다 붙이는 관리 공간은 빠져 있어요.
- 키를 오름차순으로만 넣어 리프 채움률이 50%예요. 무작위 순서로 넣는 경우는 지금 형식(id = row_index + 1)에서 생기지 않아 재지 않았어요.
