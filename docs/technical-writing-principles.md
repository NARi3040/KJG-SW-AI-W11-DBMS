# 문서 작성 원칙

> 이 원칙을 지키면 팀원과 AI가 문서만 읽고 같은 결과를 낼 수 있어요. PR에서 바뀐 문서는 Claude가 이 원칙으로 리뷰해요.

규칙을 기계적으로 적용하지 않아요. 독자가 문서를 이해하고 행동하는 데 방해가 되는지를 봐요.

AI가 읽는 리뷰 지침(`.github/docs-review.md`)은 팀 문서가 아니라서 영어로 쓰고, 이 원칙으로 리뷰하지 않아요.

## 모든 문서

### 한 문서에서는 한 주제만 다루기

독자가 한 문서에서 하나의 목적을 달성할 수 있게 해요. 다른 문서에 있는 내용은 복사하지 않고 링크해요. 같은 내용이 두 곳에 있으면 한쪽만 고쳐져 어긋나요.

| 문서 | 다루는 내용 |
|---|---|
| [PLANNING.md](PLANNING.md) | 과제 요구사항 |
| `docs/design/` | 구현 설계 |
| [CONTRIBUTING.md](../CONTRIBUTING.md) | 협업 규칙 |
| [GITHUB_GUIDE.md](GITHUB_GUIDE.md) | 협업 규칙을 따르는 단계별 명령어 |
| [AGENTS.md](../AGENTS.md) | AI가 지킬 규칙 |

**Incorrect:** 설계 문서에 브랜치 규칙을 다시 적어요.

**Correct:** 설계 문서에는 설계만 쓰고, 필요하면 CONTRIBUTING.md를 링크해요.

### 가치를 먼저 쓰기

문서 첫머리에서 독자가 무엇을 알게 되거나 할 수 있는지 알려 줘요.

**Incorrect:** "이 문서는 저장소를 설명해요."

**Correct:** "이 문서를 읽으면 테이블 파일의 바이트 배치를 알고 바로 읽기·쓰기를 구현할 수 있어요."

### 해요체로 쓰기

저장소 문서는 해요체로 통일해요. 한 문서 안에서 "~한다", "~합니다"를 섞지 않아요.

### 용어와 코드 표기 통일하기

- Statement, 토큰, 테이블 파일, 헤더, 행 번호처럼 설계 문서에서 정한 용어를 그대로 써요. 같은 대상을 다른 이름으로 부르지 않아요.
- 함수, 타입, 필드, 파일 경로, 명령어는 백틱으로 감싸요. (예: `storage_open`, `src/lexer.c`, `make test`)

### 실제와 일치시키기

문서의 명령어, 파일 경로, 링크, 마일스톤 이름은 저장소에 실제로 있는 것과 같아야 해요. 코드나 설정을 바꾸면 그것을 설명하는 문서도 같은 PR에서 고쳐요.

### 규칙 문서끼리 충돌하지 않기

AGENTS.md, CONTRIBUTING.md, GITHUB_GUIDE.md가 같은 규칙을 다르게 말하지 않게 해요. 한 문서의 규칙을 바꾸면 나머지 문서에서 그 규칙을 언급하는 곳도 확인해요.

### 측정값은 조건과 함께 쓰기

시간, 크기 같은 측정값에는 측정한 기계, 데이터 크기, 명령을 함께 적어요. 조건이 없는 숫자는 다른 기계에서 다시 확인할 수 없어요.

**Incorrect:** "전체 조회는 0.35초예요."

**Correct:** "100만 행(행 40B) 전체 조회는 0.35초예요. Ryzen 7 5800X, NVMe, `gcc -O2`에서 쟀어요."

## 설계 문서 (`docs/design/`)

AI는 설계 문서대로 구현하고, 내용이 빠졌으면 구현을 멈춰요. 그래서 설계 문서는 읽는 사람이 추측하지 않고 구현할 수 있어야 해요.

### 요구사항 ID 연결하기

설계가 다루는 [PLANNING.md](PLANNING.md)의 요구사항 ID를 적어요. 리뷰어가 빠진 요구사항을 찾을 수 있어요.

**Correct:** "이 문서는 R1-2, R1-3을 다뤄요."

### 입력과 출력을 의미, 형식, 예시로 쓰기

함수의 매개변수와 반환값, 구조체의 필드, 파일의 바이트 배치를 설명할 때는 의미, 허용 형식, 예시를 함께 써요. 이름과 타입만 있으면 구현자가 추측해야 해요.

**Incorrect:** `row_count: 8B`

**Correct:** `row_count`(위치 12, 8B, 리틀 엔디언 부호 없는 정수): 저장된 행 개수. 다음 id는 `row_count + 1`이에요. (예: 행 3개면 `03 00 00 00 00 00 00 00`)

### 엣지 케이스와 오류 적기

빈 테이블, 최대 길이 값, 범위를 넘는 정수, 닫히지 않은 문자열처럼 경계에 있는 입력을 어떻게 처리하는지 적어요. 오류마다 출력할 메시지도 적어요.

### 정하지 않은 내용 드러내기

아직 정하지 않은 내용은 비워 두지 않고 "미정"과 이유를 적어요. 빈칸은 이미 정한 것처럼 보이거나 AI가 임의로 채우게 만들어요.

### 공통 형식 변경 알리기

테이블 파일 형식, Statement 구조, 모듈 사이 함수 선언은 여러 사람이 함께 쓰는 약속이에요. 바꾸는 PR은 해당 설계 문서를 같은 PR에서 고치고, PR 본문의 "공통 형식 영향"에 이유를 적어요.
